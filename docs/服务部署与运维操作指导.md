# DomainToolBS 服务部署（Ubuntu 端）与运维操作指导

| 项目 | 内容 |
|---|---|
| 适用系统 | Ubuntu 22.04 LTS 及以上（x86_64） |
| 部署方式 | Docker Compose（推荐） / 源码部署 |
| 文档版本 | v1.1（P1–P6 + CA 认证开关 + OU 审计补全） |

---

## 1. 环境准备

### 1.1 硬件与系统
- CPU ≥ 2 核，内存 ≥ 4 GB（生产建议 8 GB）；
- 磁盘 ≥ 20 GB（含 PostgreSQL 数据增长空间）；
- 操作系统：Ubuntu 22.04/24.04 LTS。

### 1.2 依赖软件
- Docker Engine ≥ 24，Docker Compose v2（`docker compose` 子命令）；
- （源码部署需）Python 3.11+、Node.js 20、PostgreSQL 16。

### 1.3 网络要求
- 服务器需能**通过 LDAPS(636)** 访问目标 AD 域控；
- 开放端口：前端 8080（HTTP，建议前置 HTTPS 反代），后端 8000（仅内网/反代可达）。

---

## 2. 方式一：Docker Compose 部署（推荐）

### 2.1 获取代码
```bash
git clone <仓库地址> DomainToolBS
cd DomainToolBS
```

### 2.2 生成密钥（务必替换默认值）
```bash
export JWT_SECRET_KEY=$(python3 -c "import secrets;print(secrets.token_urlsafe(48))")
export FERNET_KEY=$(python3 -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())")
```

### 2.3 启动
```bash
docker compose up --build -d
```
- 前端：http://<服务器IP>:8080
- 后端 API：`/api/v1`（由前端 nginx 反代，或直连 :8000）
- 数据库：PostgreSQL 16（compose 内 `db` 服务，数据落到 `pgdata` 卷）

### 2.4 健康与验证
```bash
curl http://localhost:8000/health
# 期望返回 {"status":"ok","app":"DomainToolBS"}
```

### 2.5 环境变量说明
| 变量 | 说明 | 默认值 |
|---|---|---|
| `DATABASE_URL` | 本地库连接串（compose 已设为 PostgreSQL） | — |
| `JWT_SECRET_KEY` | JWT 签名密钥（生产必改） | `change-me-in-production` |
| `FERNET_KEY` | 域服务账号密码加密密钥（生产必配） | 空 |
| `CORS_ORIGINS` | 允许跨域来源 | `http://localhost:8080,http://frontend` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | 登录令牌有效期 | 120 |

> compose 中 `backend` 的 `FERNET_KEY` 指向 `${FERNET_KEY:-}`，请务必通过 2.2 导出，否则**重启后旧域凭据密文无法解密**。

## 3. 方式二：源码部署（生产自托管）

### 3.1 后端
```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # 修改 DATABASE_URL/JWT_SECRET_KEY/FERNET_KEY
# 生产数据库建议 PostgreSQL：DATABASE_URL=postgresql+psycopg://domaintool:xxx@localhost:5432/domaintool
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
# 或用 gunicorn：gunicorn -k uvicorn.workers.UvicornWorker -w 4 app.main:app
```

### 3.2 前端
```bash
cd frontend
npm install
npm run build                   # 产物在 dist/
# 用 nginx 托管 dist/，并反代 /api 到后端 8000
```

### 3.3 Nginx 反代示例（前端容器已内置 `nginx.conf`）
```nginx
location /api/ {
    proxy_pass http://backend:8000;   # 源码部署改为 http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

## 4. 超级管理员密码找回 / 创建（服务器侧）

超级管理员账号**不能通过 Web 界面增删或改密**，只能在服务器侧操作，满足"密码忘记只能服务端找回"的硬性安全约束。

### 4.1 Docker 部署
```bash
docker compose exec backend python scripts/reset_superadmin.py \
  --username admin --password 'NewP@ssw0rd123'
```
- 账户不存在 → 创建为超级管理员；
- 账户已存在 → 重置密码并强制为超级管理员、启用。

### 4.2 源码部署
```bash
cd backend
source .venv/bin/activate
python scripts/reset_superadmin.py --username admin --password 'NewP@ssw0rd123'
# 可选：--display-name '超级管理员'
```
脚本读取 `DATABASE_URL`（来自 `.env`）连接本地库，因此会在当前配置的数据库上生效。

## 5. 首次初始化

1. 浏览器访问前端地址；
2. 若平台无任何账号，登录页提供「首次使用？初始化平台」，提交用户名/密码创建**超级管理员**（`POST /api/v1/auth/bootstrap`）；
3. 使用超管登录后，进入「域配置」添加域控并做连通性测试。

## 6. 备份与恢复

### 6.1 数据库（PostgreSQL）
```bash
# 备份
docker compose exec -T db pg_dump -U domaintool domaintool > backup_$(date +%F).sql
# 恢复
docker compose exec -T db psql -U domaintool domaintool < backup_YYYY-MM-DD.sql
```
- 本地库仅存平台账号、授权、审计、域配置等元数据，**不含 AD 内对象数据**；
- `pgdata` 卷为持久化目录，迁移时整体保留即可。

### 6.2 配置与密钥
- 备份 `.env`（含 `JWT_SECRET_KEY`/`FERNET_KEY`）与 compose 文件；
- **FERNET_KEY 丢失 = 已存域绑定密码不可解密**，需重新填写域配置。

## 7. 日志与监控

- 后端日志：容器日志 `docker compose logs -f backend`；级别由 `LOG_LEVEL` 控制（默认 INFO）；
- 认证失败、批量任务、写操作均记录到 `audit_log` 表，可在前端「审计日志」查看；
- 未捕获异常统一返回 JSON 详情，并写入后端日志（`logger.exception`）。

## 8. 升级与回滚

```bash
git pull
docker compose up --build -d          # 升级
# 回滚：git checkout <旧版本标签> 后重新 build
```
- 数据库表结构在应用启动时由 `init_db()` 做**增量迁移**（补列、回填旧数据），升级通常无需手动迁移；
- 重大版本升级前请先做 6.1 数据库备份。

## 9. 常见故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 启动后访问 500，日志提示凭据解密失败 | `FERNET_KEY` 变更/缺失 | 恢复原 `FERNET_KEY`，或重新填写域配置 |
| 连通性测试失败 | 未走 LDAPS/端口/账号权限 | 确认 636 可达、绑定账号有相应委派权限；**证书不做校验**（自签名也可连通），故失败多为地址/端口/账号权限问题 |
| 写操作返回 403 | 当前账号作用域不包含目标 OU/权限 | 由超管在「授权管理」调整 `admin_scope` |
| 登录后菜单空白 | 角色与菜单映射异常 | 确认 `admin_user.role` 取值为四角色之一 |
| 批量任务某行失败 | 用户不存在/越权/AD 约束 | 查看任务明细 message 字段 |
| 忘记超管密码 | — | 使用 4 节服务器脚本重置 |

## 10. 安全运维清单

- [ ] 已替换 `JWT_SECRET_KEY` 与 `FERNET_KEY`；
- [ ] 前端经 HTTPS 反代；
- [ ] 后端 8000 仅内网/反代可达，不直接暴露公网；
- [ ] AD 绑定账号使用「委派控制」最小权限，非 Domain Admin；
- [ ] 知悉 LDAPS 当前**不校验域控证书**（`CERT_NONE`，自签名可连通），生产建议配置可信证书或在边界做 TLS 终结；
- [ ] 平台账号初始密码符合复杂度（≥8 位，含大小写/数字/符号），并遵循历史复用限制；
- [ ] 定期备份 PostgreSQL 与 `.env`；
- [ ] 超管密码定期通过服务器侧脚本轮换。

## 11. 域控 CA 证书导入（可选增强，双通道）

平台连接域控默认走**基础通道**（`CERT_NONE`，不校验域控证书）。该通道在可信内网/隔离管理网中可用，但存在被中间人劫持的风险。**导入域控自签名（或企业 CA 签发）证书后，平台对该域自动切换到更安全的 `CERT_REQUIRED` 校验通道**；校验失败会自动回退基础通道，绝不中断业务。

### 11.1 何时需要
- 生产环境、跨不可完全信任网络（如跨分公司 IPSec VPN 之外的链路）访问域控；
- 希望检测到域控 LDAPS 证书伪造/过期。

> 不导入 CA 也能正常添加与使用域控（仅标记为"缺CA(不安全)"），可随时由超管/管理员补导入。

### 11.2 获取域控证书（任选其一）
**方式 A：域控本地导出（推荐）**
1. 域控上运行 `certlm.msc` → 个人 → 证书；
2. 找到颁发给该域控主机名、模板为 `DomainController` 的证书；
3. 右键 → 所有任务 → 导出 → **不导出私钥** → Base64 编码 X.509 (.CER)；
4. 用记事本打开导出的 `.cer`，复制 `-----BEGIN CERTIFICATE-----` … `-----END CERTIFICATE-----` 全文。

**方式 B：从平台服务器抓取（首次须在网络可信时）**
```bash
echo | openssl s_client -connect <域控IP或FQDN>:636 2>/dev/null | openssl x509 -outform PEM > dc.pem
cat dc.pem   # 复制证书内容
```
> 内置 CA 场景：把企业根 CA 证书（而非域控叶证书）导入效果最佳——域控换叶证书无需重新导入。
> 自签名场景：把域控那张自签名证书本身作为 CA 导入即可（自签名证书即自己的根）。

### 11.3 在界面导入并验证
1. 超管或管理员进入「域配置」→ 编辑对应域；
2. 展开「CA 证书」文本框，粘贴证书 PEM；
3. 点击「导入并验证 CA」；
4. 系统即时用该 CA 做链校验，返回状态：
   - `已信任`：校验通过，后续走安全通道；
   - `即将到期(N天)`：证书将在 N 天内过期，请准备更新；
   - `已过期` / `校验失败`：安全通道不可用，写操作对非超管暂停（见 11.4）；
   - `缺CA(不安全)`：尚未导入（基础通道）。

### 11.4 证书到期与过期行为
- 平台每日后台巡检所有已导入 CA 的域，刷新信任状态；对"即将到期/已过期"的域，写入一条 `audit_log`（result=warn）告警，便于超管无需手动测试也能看到。
- **过期后的权限行为**：
  - 读取（查询）对所有角色始终允许；
  - 写操作（用户/组/计算机/OU 的写、删、移动、重置密码等）在证书 `已过期/校验失败` 时，**非超级管理员被拦截**（提示"该域证书已过期/未通过校验，写操作已暂停，请由管理员重新导入 CA"）；
  - 超级管理员不受限，可继续操作并重新导入有效 CA；
  - 管理员可在「域配置」重新导入 CA 恢复写权限（CA 导入入口限超管+管理员）。
- 域控证书续期后，重新执行 11.3 导入新证书即可。

### 11.5 CA 认证总开关（仅超级管理员）

每个域在「域配置」中可独立设置 **CA 认证总开关**（`ca_enabled`，默认开启），与"是否导入 CA 证书"是两个独立维度：

| 开关状态 | 证书已导入且受信(ok) | 证书缺 / 过期 / 校验失败 |
|---|---|---|
| **开启（默认）** | 安全通道，正常 | 非超级管理员写操作被暂停（提示"该域证书未通过校验，写操作已暂停"），仅超管可继续 |
| **关闭** | 不校验，正常 | **完全不限制**，管理员可自由写入 |

- 切换权限仅限超级管理员；管理员/普通用户不可操作该开关。
- 关闭开关常用于**可信隔离内网域**或**测试域**，避免证书过期/未导入时阻断日常运维；生产跨不可信网络访问的域应保持开启。
- 开关切换即时生效，无需重启服务；关闭后后台每日巡检不再对该域产生证书到期告警。
- 数据库：`domain_config` 表含 `ca_enabled` 列，由 `init_db()` 增量迁移自动补列（存量域默认开启，行为不变）。

## 12. 启用 HTTPS（外部访问，仅配置、不改代码）

平台前端容器即 nginx，对外只暴露 HTTP（默认 `8080:80`）。**开放外部互联网访问前必须启用 HTTPS，且只需改服务器/反向代理配置，无需改动任何业务代码。**

### 12.1 在平台前端 nginx 上终结 TLS（方式一）
1. 准备证书 `fullchain.pem` / `privkey.pem`（Let's Encrypt、企业 CA 或现有证书均可）；
2. 修改前端容器 nginx 配置，增加 443 监听并反代 `/api`：
   ```nginx
   server {
       listen 80;
       # 强制跳转到 HTTPS
       return 301 https://$host$request_uri;
   }
   server {
       listen 443 ssl;
       server_name dt.example.com;
       ssl_certificate     /etc/nginx/certs/fullchain.pem;
       ssl_certificate_key /etc/nginx/certs/privkey.pem;
       location / { root /usr/share/nginx/html; try_files $uri $uri/ /index.html; }
       location /api/ {
           proxy_pass http://backend:8000;
           proxy_set_header Host $host;
           proxy_set_header X-Real-IP $remote_addr;
       }
   }
   ```
3. 挂载证书到容器，并把 `docker-compose.yml` 前端端口改为 `443:443`；
4. 把 `CORS_ORIGINS` 改为前端 HTTPS 地址（如 `https://dt.example.com`）。

### 12.2 复用现有 Web 服务器反代（方式二，推荐）
若总公司服务器已有 nginx/网关对外提供 HTTPS，可让 DomainToolBS 留在容器网络内（不暴露公网），由现有 nginx 反代：
```nginx
location /dt/ { proxy_pass http://<前端容器IP或docker网络名>:80/; }
location /dt/api/ { proxy_pass http://backend:8000/; }
```
证书只在一处管理，最省心。

> 无论哪种方式，后端 `app` 代码均无需修改；本期**不做**公网开放，列入下一期。

## 13. 端口冲突与反向代理

### 13.1 默认发布端口
`docker-compose.yml` 在宿主机发布的端口：

| 服务 | 宿主机端口 | 说明 |
|---|---|---|
| frontend | `8080:80` | Web 控制台（HTTP） |
| backend | `8000:8000` | API（通常仅内网/反代可达） |
| db | 不发布 | PostgreSQL 仅容器网络内，不占宿主机 5432 |

### 13.2 与已有 Web 服务冲突
若总公司生产服务器已运行其他 Web 服务（常见占用 80/443，或占用了 8080/8000），直接 `docker compose up` 会报"端口已被占用"。处理：
- **方案 A（改端口）**：把 `docker-compose.yml` 中 `frontend` 的 `"8080:80"` 改为空闲端口（如 `"18080:80"`），`backend` 的 `"8000:8000"` 改为 `"18000:8000"`；db 不要加 `ports` 映射以免占用 5432；
- **方案 B（复用现有反代，推荐）**：DomainToolBS 各容器不对外发布端口，由服务器已有 nginx 按 12.2 反代到容器网络内的 `frontend:80` / `backend:8000`。

### 13.3 验证
```bash
# 查看端口占用（Linux）
ss -ltnp | grep -E ':8080|:8000|:80|:443'
docker compose ps        # 确认各服务状态
curl -k https://localhost:443/health   # HTTPS 就绪后健康检查
```
